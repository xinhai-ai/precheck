# 预申请申诉通过面板与预申请通过面板对齐设计

## 背景

当前管理端“预申请申诉审核”中的“通过”操作，仍沿用一套较简化的审核表单：

- 只填写 `reviewComment`
- 后端只接收 `reviewComment`
- 申诉通过后，仅将 `reviewComment` 写入对应 `PreApplication.guidance`

这与管理端“预申请详情”中的“审核通过面板”存在明显差异。

后者已经支持：

- 指导意见
- 邀请码输入
- 邀请码检测
- 已发码勾选
- 详情中对邀请码、发码状态、指导意见的统一展示

用户希望将“申诉通过”这部分设计得与“预申请详情里的通过面板”尽量相同，不只是视觉上相似，还要求实际行为也尽量一致：申诉通过时也能填写指导意见、邀请码、已发码，并将这些信息写回对应预申请，供后续详情展示与通知复用。

## 目标

- 让“申诉通过”弹窗在字段结构和交互上尽量对齐普通“预申请通过面板”。
- 让申诉通过时填写的指导意见、邀请码、已发码状态真正落到对应 `PreApplication` 上。
- 让后续预申请详情页、管理员查看态、站内信与邮件通知看到的信息保持一致。
- 保持改动最小，不做与本需求无关的大范围重构。

## 已确认范围

- 仅调整管理端预申请申诉列表中的“通过”审核路径。
- `REJECT` 驳回路径保持现状，包括封禁提交权限与封禁天数逻辑。
- “通过”行为需要与普通预申请通过尽量一致，不只是 UI 对齐。
- 本次不强行把申诉审核页面容器改成与预申请详情一致的 `Drawer`，优先保留现有 `Dialog`。
- 本次不做大规模抽象，不强行提炼共享复杂组件，优先最小改动实现一致体验。

## 方案对比

### 方案 A：只对齐界面，不对齐数据语义

做法：

- 申诉通过弹窗改成看起来和普通通过面板类似。
- 但后端仍只接收 `reviewComment`，邀请码和已发码不作为独立字段落库。

优点：

- 改动最小。

缺点：

- 数据语义混乱。
- 预申请详情无法自然复用同一套展示逻辑。
- “已发码”只能停留在展示层，无法形成真实状态。
- 后续通知、审计与查看态容易出现信息割裂。

### 方案 B：对齐界面与行为，但不做大范围重构（推荐）

做法：

- 申诉通过弹窗新增与普通通过面板一致的关键字段：指导意见、邀请码、邀请码检测、已发码。
- 申诉通过 API 同步接收这些字段。
- 审核通过后将数据写回目标 `PreApplication`，作为最终展示真相来源。
- `Appeal.reviewComment` 继续保留，用于申诉审核留痕。

优点：

- 管理员体验与心智最一致。
- 后续预申请详情、查看态、通知内容都可围绕同一份数据展示。
- 改动范围聚焦，不需要额外重构整个申诉页面架构。

缺点：

- 需要同时调整前端弹窗、申诉审核 API 与通知内容拼接。

### 方案 C：顺手提炼共享通过表单组件

做法：

- 抽取普通预申请通过面板与申诉通过面板的共享组件。
- 同步统一两端 UI 与交互实现。

优点：

- 长期维护性最好。

缺点：

- 本次改动范围偏大。
- 容易引出无关重构，不符合“最小闭环”目标。

## 选型

采用 **方案 B**：对齐界面与行为，但不做大范围重构。

原因：

- 能满足“尽量相同”的核心诉求。
- 能确保邀请码、已发码、指导意见真正成为预申请最终结果的一部分。
- 风险和收益平衡最好，适合作为一次聚焦改动落地。

## 详细设计

### 1. 数据语义与状态归属

申诉通过后，最终结果以对应的 `PreApplication` 记录为准。

具体规则：

- `PreApplication.status` 更新为 `APPROVED`
- `PreApplication.guidance` 保存本次填写的指导意见；若填写邀请码，则沿用普通通过逻辑将邀请码拼接到指导意见中
- 若填写了邀请码，或管理员勾选了“已发码”，则更新 `codeSent = true` 与 `codeSentAt`
- `PreApplicationVersion` 同步记录本次通过结果，确保历史版本一致

同时保留申诉记录自身的审核痕迹：

- `PreApplicationAppeal.status` 从 `PENDING` 变为 `OVERRIDDEN`
- `PreApplicationAppeal.reviewComment` 继续写入本次填写的指导意见，作为申诉审核留痕字段

这样可以保证：

- 后续详情展示以预申请主记录为准
- 申诉记录列表与审计中仍然能看到“这次申诉审核写了什么”

### 2. 申诉通过弹窗字段设计

当申诉审核操作为“通过”时，弹窗字段调整为与普通预申请通过面板尽量一致：

- `邀请码`：可选，支持粘贴邀请码或邀请码链接
- `检测邀请码`：调用现有公开检测接口进行校验
- `已发码`：无邀请码时可手动勾选；有邀请码时自动视为已发码
- `指导意见`：必填

交互规则与普通通过保持一致：

- 如果输入了邀请码，`已发码` 默认生效，并禁用手动取消
- 如果没有邀请码，管理员可手动决定是否勾选“已发码”
- 邀请码检测失败时，仅提示结果，不强制阻止提交

`REJECT` 驳回弹窗维持当前逻辑：

- 驳回说明
- 是否封禁提交权限
- 封禁天数

这样可以避免把“通过”和“驳回”两种完全不同的审核语义混成一套过度复杂的表单。

### 3. 管理端查看态展示

当申诉记录已经通过（`OVERRIDDEN`）时，查看弹窗中应增加一块与普通预申请通过结果尽量一致的结果展示区。

建议展示内容：

- 审核人
- 审核时间
- 邀请码
- 发码状态
- 指导意见

同时保留申诉上下文：

- 申诉理由
- 原驳回快照

这样管理员在查看时，既能看到“用户为什么发起申诉”，也能看到“这次申诉最终是如何被通过的”。

### 4. API 输入与行为调整

`app/api/admin/pre-application-appeals/[id]/review/route.ts` 在 `APPROVE` 分支中，需要将当前仅接收 `reviewComment` 的逻辑调整为支持更完整的输入。

建议输入字段扩展为：

- `action`
- `guidance`
- `inviteCode`
- `codeSent`
- `locale`
- `reviewComment` 保留兼容或在服务端内部由 `guidance` 派生

推荐实现方式：

- 前端在“通过”模式下主要提交 `guidance`、`inviteCode`、`codeSent`
- 服务端将 `guidance` 作为申诉通过的主要审核内容
- `PreApplicationAppeal.reviewComment` 写入 `guidance`
- 若填写邀请码，则按照普通预申请通过接口已有逻辑，将邀请码拼接到 guidance 中用于持久化、站内信与邮件通知

这样可以尽量复用普通预申请通过的语义，而不再让申诉通过走一套独立表述。

### 5. 通知内容对齐

申诉通过后的站内信与邮件内容，应与普通预申请通过的结果尽量一致。

具体要求：

- 通知正文以指导意见为主
- 若填写邀请码，则将邀请码附加到指导意见内容中
- 避免出现“后台已保存邀请码，但用户通知里没有邀请码”的割裂

实现上可优先沿用当前普通预申请通过通知中对 `guidanceWithCode` 的处理方式，避免新增另一套通知拼接分支。

### 6. 审计与一致性

本次改动后，仍需保留“申诉通过”和“普通审核通过”在审计日志中的区别。

要求：

- 继续写入 `PRE_APPLICATION_APPEAL_REVIEW_OVERRIDE` 审计动作
- 继续写入 `PRE_APPLICATION_REOPEN_FROM_APPEAL` 审计动作，或按现有命名保持兼容
- 审计元数据中增加或保留以下信息：
  - `guidance`
  - `inviteCode`
  - `codeSent`

这样既能保持审计语义清晰，也便于后续排查“通过时是否填写了邀请码、是否标记已发码”。

### 7. 复用策略

本次不建议大规模提炼共享通过表单组件。

推荐策略：

- 先在申诉审核组件中按普通通过面板的字段结构与交互复制必要实现
- 尽量复用已有工具函数与接口：
  - 邀请码提纯工具
  - 邀请码检测接口
  - 现有 `guidance + inviteCode` 拼接逻辑
- 若在实现过程中发现两边逻辑高度重合，再考虑后续独立重构

这能最大限度控制本次改动范围，避免为“抽象复用”引入新的回归风险。

## 测试策略

优先验证以下四条主路径：

- 申诉通过，仅填写指导意见
- 申诉通过，填写邀请码
- 申诉通过，无邀请码但勾选已发码
- 申诉驳回，现有封禁逻辑保持不变

重点回归以下展示结果：

- 申诉审核弹窗中的“通过”表单
- 已通过申诉的查看态展示
- 普通预申请详情页中的邀请码、发码状态与指导意见是否同步

同时确认以下副作用：

- 站内信 / 邮件是否包含正确的指导意见与邀请码内容
- 审计日志是否仍能区分申诉通过与普通审核通过

## 风险与回滚

主要风险：

- 前端新增字段后，如果后端未同步接收，会出现“能填不能存”的不一致
- 若仅更新 `PreApplication.guidance` 而遗漏 `codeSent` 等字段，会导致查看态与列表展示不完整
- 若通知仍沿用旧的 `reviewComment` 文案拼接方式，可能与最终落库结果不一致

回滚方式：

- 前端可回退为当前简化表单
- 后端恢复为仅接收 `reviewComment` 的实现
- 不涉及数据库 schema 变更，因此回滚成本较低
