# 后台用户公告确认弹窗设计

## 背景

当前项目已经有完整的登录、注册、后台控制台与管理员设置体系，但缺少一种“普通用户进入后台前必须先确认公告”的轻量拦截机制。

本次需求希望在不引入服务端确认记录的前提下，实现一个仅保存在浏览器本地的公告确认弹窗，用于在普通用户进入 `/{locale}/dashboard/**` 时强制展示公告并要求输入指定确认口令。管理员需要能够在后台控制是否启用、编辑公告内容、配置提交延迟秒数，并手动决定是否让已经确认过的用户重新弹出确认。

## 目标

- 普通用户进入任意 `/{locale}/dashboard/**` 页面前，若当前浏览器尚未确认当前公告版本，则必须先完成确认。
- `ADMIN` 与 `SUPER_ADMIN` 角色完全豁免，不显示公告弹窗。
- 公告配置由管理员在后台设置页统一维护。
- 公告内容为纯文本多行内容，前端按原样展示换行。
- 用户必须输入管理员设置的确认口令，且需要等待配置的延迟秒数结束后才能提交。
- 确认结果仅保存在浏览器 `localStorage` 中，不写入数据库，不与账号同步。
- 管理员可以单独触发“重新确认”，让已确认用户在本浏览器再次弹出。

## 已确认范围

- 拦截位置是后台控制台，而不是登录页或注册页。
- 弹窗对普通用户是强拦截：不可关闭、不可跳过、确认前不可操作后台页面。
- 公告内容不支持 Markdown，不接入富文本编辑器。
- 确认口令会直接展示给用户，例如“请输入：xxx”。
- 是否重新弹出不由内容变化自动决定，而是由管理员主动触发。
- 浏览器清缓存、更换浏览器或更换设备后重新弹出，属于预期行为。

## 方案对比

### 方案 A：`localStorage + 后台版本号`

做法：

- 后台保存公告启用状态、公告内容、确认口令、延迟秒数、公告版本号。
- 前端进入后台时读取当前版本，并与 `localStorage` 中已确认版本比较。
- 管理员需要重新确认时，手动提升版本号。

优点：

- 最符合“确认只保存在浏览器里”的要求。
- 能精确满足“管理员决定是否重新弹出”的规则。
- 前后端职责清晰，改动范围可控。

缺点：

- 版本号需要单独维护。
- 不同浏览器/设备之间不会同步确认状态。

### 方案 B：`localStorage + 内容哈希`

做法：

- 不维护版本号，前端直接根据公告内容、确认口令和延迟秒数生成哈希。
- 哈希变化即视为新公告。

优点：

- 不需要额外版本字段。
- 内容变化自动失效。

缺点：

- 不能满足“管理员自行决定是否重新弹出”的需求。
- 调整错别字或秒数也会被动触发重新确认，控制粒度过粗。

### 方案 C：独立确认页 + 路由重定向

做法：

- 未确认用户访问后台时，先跳转到独立确认页，确认后再回原页面。

优点：

- 流程最硬，拦截行为明显。

缺点：

- 与“弹窗公告”目标不一致。
- 需要额外路由和跳转处理，复杂度更高。

## 选型

采用 **方案 A：`localStorage + 后台版本号`**。

原因：

- 与“普通用户后台强拦截、管理员豁免、确认只保存在浏览器、管理员可决定是否重新弹出”的约束完全一致。
- 可以复用现有 `SiteSettings` / 管理设置表单 / 后台布局结构，保持改动最小。
- 将“保存配置”和“重新触发确认”解耦后，管理员日常修正文案时不会误伤所有已确认用户。

## 详细设计

### 1. 数据模型与后台配置

文件范围：`prisma/schema.prisma`、`app/api/admin/system-config/route.ts`、`components/admin/settings-form.tsx`、`lib/site-settings.ts`

在 `SiteSettings` 中新增以下字段：

- `newUserAnnouncementEnabled: Boolean @default(false)`
- `newUserAnnouncementContent: String @default("")`
- `newUserAnnouncementConfirmText: String @default("")`
- `newUserAnnouncementDelaySeconds: Int @default(0)`
- `newUserAnnouncementVersion: Int @default(1)`

设计要点：

- 字段继续放在现有全局站点设置表中，不新增独立表。
- 管理端编辑入口复用现有“系统配置”保存链路。
- 前端后台布局读取配置时，只传递公告弹窗所需的最小字段。
- `lib/site-settings.ts` 需要扩展缓存结构，保证后台布局读取到完整公告配置。

### 2. 管理员操作流

管理员设置页新增一个独立卡片，例如“用户公告确认”。

卡片内包含：

- 启用开关
- 公告正文输入框（纯文本多行）
- 确认口令输入框
- 延迟秒数输入框
- 当前版本展示
- 单独的“重新触发确认”按钮

行为规则：

- 普通保存只更新配置内容，不自动提升版本号。
- 当管理员明确点击“重新触发确认”时，才会让 `newUserAnnouncementVersion + 1`。
- 启用状态下，正文和确认口令必须非空。
- 延迟秒数限制在合理范围内，建议 `0-300`。

为避免把“保存配置”和“触发重新确认”混成一次请求，建议为“重新触发确认”提供单独后台动作，例如独立 API 路由或专门的更新分支。

### 3. 后台拦截与组件结构

文件范围：`app/[locale]/dashboard/layout.tsx`、`components/dashboard/dashboard-layout-client.tsx`

设计方式：

- 后台布局服务端已具备用户与站点配置读取能力，继续在这里拿到当前用户和公告配置。
- 将公告配置与当前用户角色一起传入 `DashboardLayoutClient`。
- 在 `DashboardLayoutClient` 中挂载一个新的客户端守卫组件，例如 `NewUserAnnouncementGate`。

守卫逻辑：

- 若当前用户角色是 `ADMIN` 或 `SUPER_ADMIN`，直接跳过。
- 若公告未启用，直接跳过。
- 若 `localStorage` 中记录的确认版本与当前版本一致，直接放行。
- 其他情况显示不可关闭的公告弹窗，阻止后台内容交互。

为避免“先看到后台页面，再突然被弹窗盖住”的闪动，守卫组件在完成本地校验前应先渲染遮罩或加载态。

### 4. 弹窗交互细节

文件范围：建议新增 `components/dashboard/new-user-announcement-gate.tsx`

交互要求：

- 使用现有 UI 体系中的 `Dialog` 或同风格模态框实现。
- 禁止点击遮罩关闭，禁止 `Esc` 关闭。
- 标题明确提示用户需要先阅读并确认公告。
- 正文使用纯文本展示，保留换行，例如通过 `whitespace-pre-wrap` 呈现。
- 直接展示管理员配置的确认口令提示，例如“请输入：xxx”。
- 倒计时未结束前，提交按钮保持禁用并显示剩余秒数。
- 倒计时结束后，只有当输入内容与确认口令完全一致时才允许提交。

确认成功后：

- 写入 `localStorage`，建议结构为：`user-announcement-ack = { version, confirmedAt }`
- 状态切换为已放行，后台内容恢复可用。

### 5. 错误处理与降级策略

错误处理规则：

- 若启用公告但配置缺少正文或确认口令，后台保存时直接校验失败。
- 若用户输入不匹配，弹窗内显示明确错误提示，不关闭弹窗。
- 若浏览器写入 `localStorage` 失败，则提示确认失败并保持拦截，不放行。
- 若后台读取配置失败，服务端继续沿用 `getSiteSettings()` 的默认值策略，公告功能默认视为关闭，避免把普通用户误锁死在后台外。

该降级策略的核心取舍是：

- 配置异常时优先保证后台可用性；
- 浏览器本地确认持久化失败时优先保证规则完整性。

### 6. 测试策略

优先使用仓库现有的源码/回归测试风格，增加聚焦本功能的测试文件，例如 `tests/lib/dashboard-user-announcement-confirmation.test.ts`。

建议覆盖：

- `SiteSettings` / `system-config` 暴露并校验新增字段。
- `DashboardLayoutClient` 或新守卫组件的源码包含 `USER` 角色生效、管理员豁免逻辑。
- 客户端守卫使用版本号与 `localStorage` 进行确认判断。
- 弹窗为不可关闭模式，且存在倒计时与确认口令校验。
- 单独“重新触发确认”动作会提升版本号，而普通保存不会。

若缺少成熟的组件测试基础设施，可先采用源码级断言锁定关键行为，再补充更细的运行时验证。

## 风险与回滚

主要风险：

- 若守卫初始化时机处理不当，可能出现后台内容闪现。
- 若保存接口与重新触发逻辑耦合，可能导致管理员普通保存时意外强制全员重新确认。
- `localStorage` 读写异常时若处理不严谨，可能造成用户卡死或绕过。

回滚方式：

- 关闭 `newUserAnnouncementEnabled` 即可全局停用该功能。
- 若需要彻底移除，只需删除新增字段、后台设置项和守卫组件，不涉及用户数据迁移，因为确认状态不入库。
